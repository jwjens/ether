## Item 10 — Settings → Beta Program & Feedback

### Report (verbatim from the list)

"Settings → Beta Program & Feedback: its backend routes `/beta/apply` and `/feedback` do not exist; also offers
'free Station-tier access forever' (BetaProgram.tsx)."

### What was wrong (receipts at the pre-fix commits)

- Desktop posted to the routes: `src/components/BetaProgram.tsx:16-17` (openair `0e55bb9`) —
  `SUBMIT_URL = ${ETHER_BACKEND_URL}/beta/apply`, `FEEDBACK_URL = ${ETHER_BACKEND_URL}/feedback`.
- The backend had neither: `git show fd4e871:src/index.js | grep -c '"/beta/apply"\|"/feedback"'` → `0`.
- So every send got a 404 and fell into the catch: `BetaProgram.tsx:129` threw "backend unreachable", `:137` set
  `window.location.href = mailto` (opened a mail draft without being asked), `:168` told the user "The backend isn't
  reachable right now", and `:139` still saved `ether_beta_applied`, so the Apply tab read **✓ Applied / Application on
  file** although nothing was received.
- `:237` sent `app_version: "1.0"` (hard-coded).

### What changed

**Backend (ether-backend `0395744`)**

- `src/lib/feedback.js` (new): validation + DDL. Apply requires station name and a valid email; station type must be
  one of college/lpfm/internet/commercial/other; feedback requires text and a category of bug/feature/praise/other;
  optional email validated if given. Length caps per field; over-long input is a 400 naming the field (never silently
  cut).
- Tables `beta_applications`, `app_feedback` — created at boot in `initDB` the same way other modules' DDL is
  (`src/index.js:993`, `for (const ddl of FEEDBACK.FEEDBACK_DDL)`; `CREATE TABLE IF NOT EXISTS`).
- `POST /beta/apply` (`src/index.js:4120`) and `POST /feedback` (`:4137`): store the row, answer **201 `{ok:true,id}`**;
  bad input → 400 `{error:"invalid", fields:[…]}` and nothing stored; DB error → 500.
- Rate limit `feedbackLimiter`: 20 per IP per 15 minutes (same `express-rate-limit` pattern as `authLimiter` /
  `jukeboxPublicLimiter`).
- Notice email: one Resend email after the row is stored, to `FEEDBACK_NOTIFY_EMAIL` (env) or, if unset, the existing
  `SUPPORT_EMAIL` constant (`support@ether-technologies.com`). Fire-and-forget; a Resend error or throw is logged
  (`[feedback-notify]`) and never fails the submission.
- `GET /api/platform/feedback` (`:4152`, `requirePlatform`): newest 200 of each. Added because it was trivial and matches
  the other `requirePlatform` reads. There is **no platform-console UI** for it yet.
- Route inventory (`src/access/route-access.js`) classifies the three routes (two public with reasons, one platform);
  `test/route-inventory.test.js` count 195 → 198.

**Desktop (openair `6afa177`)**

- `src/lib/betaSubmit.ts` (new): `submitForm` / `readAnswer`. "Received" only on 2xx with `{ok:true}`. 400 → the fields
  in plain words; 429 → "Too many sent from this network…"; any other status → "The Ether server answered N. Not sent.";
  network error → "Couldn't reach the Ether server… Not sent."
- `BetaProgram.tsx`: no automatic mail draft. A failure shows its reason in red, **keeps what was typed**, and offers an
  **Email it instead** button (the user presses it). The application is remembered as filed only with the server's
  confirmation (`server_id`); old markers saved by the broken fallback no longer count, so those installs see the form
  again instead of a false "Application on file". Sends the real version (`ether.system.getVersion()`). A dev build is
  blocked by the existing dev write guard (`blockedByDevGuard`) and says so.
- Offer wording ("free Station-tier access forever") **unchanged** — see question 1.
- Door: unchanged and already canonical — ☰ Menu → Settings → System → Beta Program & Feedback.
- Help: `docs/help-beta-program.md` (new).

### Tests

- Backend: `test/feedback-routes.test.js` (6 tests: stored + 201 + one email + no license row changed; 400s store
  nothing; feedback stored verbatim with optional email; email failure still 201; platform read admitted for a platform

- Desktop: `src/lib/betaSubmit.test.ts` — **9 pass, 0 fail** (vitest). `npx tsc --noEmit`: **0 errors**.

## Item 18 — Web dashboard Users page (users part only)

### Report (verbatim)

"Web dashboard: Users page says 'Remote user management is coming in a later update' (UserManagement.tsx:27);
'Clone programming from granted library' can't be reached (CategoriesPanel.tsx:116, staged mode never on)."

(The sentence is at `ether-dashboard src/components/UserManagement.tsx:24` in the current tree.)

### What exists

(ether-backend line numbers are at `0395744`.)

There are **two different kinds of "user"** in the backend, and the page shows only one:

1. **PIN operators** (`account_users`) — what the Users page lists today. Routes, gated `requireAuthAdmin`:
   `GET /api/account/users` (`ether-backend src/index.js:2992`), `POST /api/account/users` (`:3005`, create with
   username + 4-digit PIN), `POST /api/account/users/:id/pin` (`:3033`, reset PIN). **No delete/remove route.** The
   dashboard already has `createUser` / `resetUserPin` in `src/api.ts` but no UI calls them. Install → backend only:
   `POST /api/account/users/sync` (`:3055`, desktop `src/lib/syncUsers.ts:48`). Nothing brings a web-created PIN user
   down to an install (design doc `docs/account-users-rbac.md` §4 item 6), so a user added on the web would exist only
   for dashboard sign-in, not in Ether on the computer.
2. **Account members** (email people with a position + station scope; `memberships`, `positions`) —
   `GET/POST /api/accounts/:accountId/members` (`:3074`, `:3092`), `DELETE …/members/:membershipId` (`:3141`),
   `GET/POST …/positions` (`:3164`, `:3177`), gated `requireMember("manage_users")`.

### Why nothing was built

- **The page's auth can't always call the member routes.** `requireMember` (`:1364-1368`) admits only `typ: "owner"`
  or `"user"` tokens; a dashboard PIN sign-in gets `403 member_login_required`. Only owner (email + password) sign-in
  could use them.
- **"Invite" is a dead end today.** `POST …/members` creates a `users` row with `password_hash = ''` and no
  `license_key_id` (`:3121-3122`) and **sends no email**. That person then:
  - can't sign up — `/api/user/signup` answers `409 email_taken` for an existing row (`:2372`);
  - can't sign in to the dashboard — `/api/auth/owner-login` refuses an empty hash, then answers `403 no_license` for a
    row with no `license_key_id` (`:2797-2800`);
  - could only get in by stumbling on "forgot password" (`/api/user/forgot` → `/api/user/reset`, `:2550`, `:2565`),
    after which the **desktop** activation does accept a verified member (`desktop-activate`, `:2603`, license pick `:2611-2620`) — but
    nothing tells them so.
  Wiring an "Invite" button to this would add someone who has no honest way in — the dead-control pattern again.
- **Design decisions still open** in `docs/account-users-rbac.md`:
  - §7.1 — one cloud user model, or PIN operators and email members as two projections of one person? (This decides
    what the Users page *is*.)
  - §7.4 — how account users reach the desktop install (down-sync).
  - §6 — "In-app self-service user management: Network & Enterprise only (gate by `licenses.plan`)". The member routes
    have **no plan gate**; with the new names (Local / Live 128 / Live 320 / Network) the gate needs restating anyway.
- Per CLAUDE.md "ARCHITECTURE BEFORE CODE": building over open design decisions is a STOP.

### Exactly what is missing (to make the Users page real)

1. A decision on §7.1 (which users this page manages: PIN operators, email members, or both, and how they relate).
2. An **invite** path: an email with a link that lets the invited person set a password and accept (today: no email,
   and signup/owner-login both refuse them).
3. Dashboard sign-in for members: `owner-login` only admits a `users` row that owns a license; a member needs a token
   for the account they belong to (the `switch-account` route exists for already-signed-in members, `:3228`).
4. If PIN operators stay on this page: a **remove** route for `account_users` and a down-sync to installs (§4 item 6),
   or the web-made user never appears in Ether on the computer.
5. The plan gate from §6, restated against the new plan names.

### Not touched (as instructed)

"Clone programming from granted library" (`ether-dashboard src/components/CategoriesPanel.tsx:116-117`) lives in staged
mode, and the dashboard mounts the panel with `staged={false}` (`src/components/StationDetail.tsx:310-311`). The staged
pipeline is **deprecated** for categories/programming per CLAUDE.md ("Categories/programming mirror — the rails"). Left
as is; no change.
