# Diagnosis — auto-gen self-enabling, calendar mismatch, deleted show (2026-08-12)

**Machine:** dev (`OVEVENTS`, client_id `8e8f6181-b68a-433f-a93d-8005787b641b`), schema v36.
**Method:** read-only open of the live DB (`readonly: true`) — nothing written. Ether stayed running.
All three root causes are **confirmed in code + data**; the two places I cannot prove from the DB are
marked UNVERIFIED with the one check that settles each.

## BUG 1 — auto-generation turned itself on at startup

### What is stored

| Station | value | created_at (UTC) | updated_at (UTC) |
|---|---|---|---|
| 1 Open Format | **"1"** | 2026-08-11T18:42:28 | 2026-08-12T19:53:31 |
| 2 halloVeen | **"1"** | **2026-08-12T18:19:20** | 2026-08-12T19:53:35 |
| 3 Magical Forest | **"1"** | **2026-08-12T18:19:21** | 2026-08-12T19:53:36 |
| 4 Christmas in Jully | **"1"** | **2026-08-12T18:19:22** | 2026-08-12T19:53:36 |

**All four are ON.** At 17:28Z this morning (an earlier read in this session) station 1 was `"0"` and
**stations 2–4 had no row at all**.

### CONFIRMED cause for stations 2, 3 and 4

`_migrateAutoGenerateDefault()` (`electron/main.js:7411`), called from `startAutoExtend()` at
`:7631`:

```js
const existing = db.prepare("SELECT 1 FROM station_config_kv WHERE station_id = ? AND key = 'auto_generate_enabled' LIMIT 1").get(st.id);
if (existing) continue;                       // operator has already chosen — never override
const hasLog = db.prepare("SELECT 1 FROM generated_schedule WHERE station_id = ? AND deleted_at IS NULL LIMIT 1").get(st.id);
if (!hasLog) continue;                        // never generated: fresh or unused, stays OFF
stationConfigKvSetLocal(db, st.id, 'auto_generate_enabled', '1');
```

Every station has a large log (18,021 / 33,095 / 27,614 / 31,393 rows), so `hasLog` is true for all
four. Stations 2–4 had no key, so the migration wrote `"1"`.

**The timestamps prove it was the startup path, not a click.** `startAutoExtend()` runs the migration,
then `_migrateKillLease()`, then the designation tick. On disk:

```
18:19:20  auto_generate_enabled station 2   ← migration loop, one station per row
18:19:21  auto_generate_enabled station 3
18:19:22  auto_generate_enabled station 4
18:19:28  designated_generator  all four    ← the designation tick, 6s later
```

Three sequential writes one second apart followed by the designation tick is the startup sequence,
not a human. **Jeff's report is exactly right: it turned itself on at startup.**

### THE REAL DEFECT: the migration has no "already ran" marker

It is not a migration, it is a **startup rule**. It re-evaluates on **every launch**, and its only
guard is "does the key exist". So any station whose key is absent — a new station, a restored DB, a
station whose row was cleaned — gets auto-generation switched **ON** at the next launch, forever.

That directly contradicts the decision 4.4.185 shipped, quoted from `main.js:7099`:

> *"UNSET = OFF … an unattended writer to the playout log is switched on deliberately, never
> inherited."*

The migration re-inherits it. And because the write goes through `setLocal`, it is silent — there is
no operator-visible event saying "we switched this on for you", only a console line.

### Station 1 — UNVERIFIED

Station 1's row was created 2026-08-11 and only **updated** on 08-12 (created_at is unchanged, so it
was not re-created). The migration's guard `SELECT 1 … LIMIT 1` does not filter `deleted_at`, so an
existing row of any kind makes it skip. **The migration cannot have written station 1.**

There are exactly two writers of this key in the whole tree:

1. `main.js:7420` — the migration (ruled out above)
2. `HealthMonitor.tsx:606` — the operator's AUTO ON/OFF button

So station 1 went `"0"` → `"1"` through the Health Monitor toggle. I cannot prove that from the DB —
only `updated_at` is stored, there is no value history.

**The check that settles it:** the main-process console carries `[auto-generate] write station=1
key="auto_generate_enabled" value="1"` for a click, and `[auto-extend] migration: Open Format had a
generated log` for the migration. One of those two lines is in the log for 19:53:31Z.

### Recommendation

1. **Give it a one-shot marker.** Record `auto_generate_migrated = '1'` in `install_config_kv` and
   return early if set. One line; makes re-firing impossible.
2. **Better — retire it.** It existed to carry pre-4.4.185 installs across one upgrade. That was 15
   versions ago and it has now done its job. Every launch it runs is a chance to switch a station on
   behind the operator.
3. **Make it loud if it stays.** A station being switched on for you belongs in the Health Monitor
   and the ledger as an operator-visible event, not only a console line. It already writes
   `auto-extend-migrated` to the ledger — nothing displays it, which the new Designation Activity
   section could fix.

**This must be fixed before Bug 2 can be worked around** — see below.

## BUG 2 — calendars do not match between OV and dev

### Sync is OFF and has never run

| Key | Value |
|---|---|
| `sync_enabled` | **absent** |
| `sync_backend_url` | absent |
| `sync_uuid_identity` | absent |
| `member_operate` | absent |

`main.js:2791` reads `sync_enabled` and logs *"[SYNC] disabled (set sync_enabled=true in
station_config_kv to activate)"* when it is absent. **The peer sync engine is not running.**

### The mutation log confirms nothing has ever synced

```
sync_status = 'pending'   380,784 rows
  oldest 2026-07-06T17:44:29Z   newest 2026-08-12T22:49:00Z
```

**Every mutation ever recorded on this machine is still pending. Not one has been sent.** There are no
`synced`, `syncing` or `conflicted` rows at all.

### So the calendars cannot match, and never could

Dev and OV are two independent databases that have never exchanged a row. Each runs its own
generator. Generation is not deterministic across machines — the LRP ladder, separation state and
`play_log` history differ per machine — so two machines generating the same station produce
**different logs by construction**.

That is not a sync failure. It is **two writers with no sync**, which is precisely the hazard the
designation work exists to remove. And Phase A **gates nothing** (`main.js:7435`), so designation
currently records who should own generation without stopping anyone.

Dev's state, for the record:

| Station | rows | first | last | operator rows |
|---|---|---|---|---|
| 1 | 18,021 | 2026-07-06 12:00 | 2026-08-23 23:59 | 0 |
| 2 | 33,095 | 2026-07-06 13:00 | 2026-08-16 23:57 | **28** |
| 3 | 27,614 | 2026-07-07 00:00 | 2026-08-24 23:58 | **4** |
| 4 | 31,393 | 2026-07-24 15:00 | 2026-08-20 23:59 | **14** |

I cannot compare against OV — that is a different machine's database and I have no read path to it.

### Two things worth knowing

**Designation is working.** All four stations now hold a `designated_generator` record naming
`OVEVENTS`, created 18:19:28Z. **That is the runtime receipt the 4.4.193 fix was missing** — the write
that was impossible for five versions now lands. `last_generated` is `null` on all four, consistent
with no generate having run since.

**`log_reader_flip = "1"` on all four stations.** The time-anchored log-reader is ACTIVE on every
station on this machine. `engine.js:36` says it ships OFF, gated on the flag *and* a clean shadow
burn-in *and* your separate GO. Whatever the Health Monitor's Canary section renders, the stored truth
is: all four ON. This also explains the 46 operator rows above — with the flip on, a jock hand-loading
a deck writes a `source='operator'` row (`engine.js:1308`), and **as of 4.4.196 Generate will never
remove those**. That is §7 risk 2 of the manual-log-editing design, now live with real rows.

### Recommendation

1. **Decide which machine generates**, and switch auto-generation OFF on the other. **But fix Bug 1
   first** — switching it off on dev today is undone at the next launch for any station whose key
   gets cleared, and the migration is what put three of them on in the first place.
2. **Phase B is the real fix** — gate `_autoExtendTick` on designation. Until it ships, "one machine
   generates" is a convention nothing enforces.
3. **Do not turn sync on casually.** 380,784 pending mutations would all attempt to flush. If sync is
   wanted, that backlog needs a plan (compaction, or a checkpoint/baseline) before the switch.
4. If the intent is that OV and dev *should* mirror, that is a sync project, not a calendar bug.

## BUG 3 — deleted show still in the Calendar

### The show IS deleted in the database

```json
{ "id": 5, "uuid": "e0ccb5c1-b04c-45f5-862e-614daa9fc828", "station_id": 2,
  "name": "test show", "clock_id": null, "is_active": 1,
  "days": "0123456", "start_hour": 0, "end_hour": 6,
  "deleted_at": "2026-08-11T02:58:00.015Z" }
```

It is the only soft-deleted show. **The delete worked.** This is a calendar query bug.

### The calendar query does not filter deleted rows

`src/components/BroadcastCalendar.tsx:122-128`:

```sql
SELECT s.id, s.name, s.start_hour, s.end_hour, s.days, s.color, c.name AS clock_name
  FROM shows s
  LEFT JOIN clocks c ON c.id = s.clock_id
 WHERE s.is_active = 1 AND s.station_id = ?
 ORDER BY s.start_hour
```

**No `deleted_at IS NULL`.** The deleted show has `is_active = 1` and `station_id = 2`, so it passes
both conditions and renders. `{ skipScoping: true }` is passed, so the scoping helper adds nothing.

The Shows page uses `ShowsTab.tsx:43`, which **does** filter — which is exactly why it is gone there
and present in the Calendar.

### This is systemic, not one query

Every `FROM shows` in `src/`:

**Missing the filter (will show deleted shows):**

| File | Line |
|---|---|
| `components/BroadcastCalendar.tsx` | 127 ← **the reported bug** |
| `audio/showClock.ts` | 182 ← **playout-adjacent; line 39 in the same file filters correctly** |
| `components/ProgramLog.tsx` | 101, 115, 170, 1467 |
| `components/MasterOutput.tsx` | 579, 690 |
| `components/BroadcastMonitor.tsx` | 508 |
| `components/SchedulePreview.tsx` | 108 |
| `components/OnShiftScreen.tsx` | 125 |
| `components/ProducerDesk.tsx` | 356 |
| `components/VoiceTracker.tsx` | 446 |

**Correct:** `App.tsx:911`, `audio/loggen.ts:378,442`, `audio/showClock.ts:39`,
`lib/scheduleData.ts:32`, `components/scheduler/ShowsTab.tsx:43`.

`showClock.ts` is the one to look at first: line 39 filters and line 182 does not, in the same file,
and that module resolves which clock governs an hour.

### Recommendation

1. **Fix the calendar** — add `AND s.deleted_at IS NULL`. One line, fixes the report.
2. **Then sweep the other nine**, `showClock.ts:182` first. A deleted show that can still select a
   clock is a scheduling defect, not a cosmetic one.
3. **Stop it recurring.** Soft delete is only as good as its readers, and 10 of 15 readers here forget
   it. Either a shared `activeShows()` accessor (the `scheduleData.ts` pattern, already correct), or a
   guard test that greps for `FROM shows` without `deleted_at` — the same shape as the
   `local-only-keys` test that catches the KV allowlist drifting.
