# Port 3400: no login, reachable from the network (2026-10-11)

**Question (Jeff):** confirm or refute the Oct 5 finding (`docs/settings-streaming-tiers-plan.md` §361, §393).
Jeff's position is that you must log in to access the app and the platform sites.

**Verdict: the Oct 5 finding is CONFIRMED.** Port 3400 listens on every network interface, sends `Access-Control-Allow-Origin: *`,
and has no authentication on any route. This contradicts the position that a login is required.

Read-only investigation. No command was sent to any station, and no code was changed. Source is at `572fefb` (v4.6.59).

## 1. Where it listens

- **Code:** `electron/main.js:8878`: `irisHttpServer.listen(3400, '0.0.0.0', …)`, and `:8879` logs
  `REST server listening on http://0.0.0.0:3400`.
- **Live on OVEVENTS (2026-10-11):** `netstat -ano` gives `TCP 0.0.0.0:3400 0.0.0.0:0 LISTENING 36380`.
  PID 36380 is `C:\Users\jensj\AppData\Local\Programs\Ether\Ether.exe`.
- **Firewall:** the inbound rule "Ether" is set to **Allow** on the **Domain** profile.
- **Network:** the profile is `ov.org`, **DomainAuthenticated**, so devices on the OV network can reach the port.

## 2. Authentication per route

The handler is `electron/main.js:8620–8880`, and every response sends `Access-Control-Allow-Origin: *` (`:8622`).
There is no 401/403 response anywhere in it, and no token, license or password check. `x-ether-watchdog` (`:8700`) is
recorded, never checked. **None of these routes uses the app.ether-cast.com or platform login.**

| Route | Effect | Authentication |
|---|---|---|
| `POST /api/transport/play\|pause\|stop\|skip` (`:8738`) | calls `audio.audioPlay/Pause/Stop(deck)` directly | **none**. The comment at `:8728` calls it "the unguarded one" |
| `POST /` with `{"action":"play"\|"stop"\|"skip"}` (`routeIrisCommand`, `:8326`, `:8333`) | transport | only `cmd.source === 'operator'`, a string **the caller supplies**. The comment at `:8308` says it was "proved with curl" |
| `POST /` with `{"action":"generate","payload":{"month":"YYYY-MM"}}` (`:8351`) | regenerates a station's program log | **none**. It is not in `IRIS_TRANSPORT_VERBS`, so even the `source` check does not apply |
| `POST /api/macro/:id/run` (`:8785`) | sends `macro:execute` to the renderer | **none** |
| `GET /remote` (`:8636`) | a phone page whose buttons call `/api/transport/*` | **none** |
| `GET /api/status`, `/api/now-playing`, `/api/log`, `/api/macros`, `/api/gpio/status`, `/api/repl/changes`, `/api/repl/site-id`, `/api/stream` | read station data and events | **none** |

The operator-token gate that would replace the caller-supplied `source` check and close `/api/transport` was built
2026-09-04 and is **held** (`main.js:8303–8314`, `docs/iris-transport-provenance-2026-09-04.md`).

## 3. Could an unauthenticated device on the network change what's on air?

**Yes, by statically reading the code.** No login, no account and no license is needed: any device on the same network, such as a phone on the
building Wi-Fi, can open `http://<studio-pc>:3400/remote` or send one HTTP request.

- **The program log: yes, in any mode.** `POST /` with `generate` rebuilds a station's schedule, and that schedule is what airs.
- **Play / pause / stop / skip: they reach the audio engine with no check. Whether they touch the decks on air is
  UNVERIFIED:**
  - the routes call `audio`, which is the native addon loaded **in the main process** (`main.js:389`). The deck letter is
    passed without a station id, so the engine falls back to station 1 (`native/src/lib.rs:105`,
    `station_id.unwrap_or(1)`);
  - in the default daemon mode, playout runs in the separate `ether-engine` process, so these calls may not reach the
    decks on air. In the in-process fallback mode, they would;
  - **the check that settles it:** on a machine that is NOT on air, start automation, send
    `POST /api/transport/stop`, and see whether the deck stops.
- **Skip and macros:** they send `iris:next-track` / `macro:execute` to the windows. The preload exposes
  `onNextTrack` (`electron/preload.js:371`), but nothing in `src/` subscribes to either channel, so they most likely do
  nothing. **UNVERIFIED** at runtime.
- **From a web page, not just a device:** with `Access-Control-Allow-Origin: *` and no credential, a web page open in a
  browser on the studio PC or anywhere on the LAN can send the same requests in the background.
